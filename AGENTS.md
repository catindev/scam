# Agent entrypoint

Эта папка содержит общую методологию. Проектные инструкции, принятые
архитектурные решения и явные указания пользователя имеют приоритет. Если они
противоречат друг другу, не угадывай: зафиксируй конфликт и запроси решение.

## Вход из пользовательской задачи

Пользователь не обязан заполнять SCAM-шаблоны. Если он описал задачу обычным
языком и попросил работать по SCAM:

1. Прочитай `METHOD.md`, `INTAKE.md` и `DOCUMENTATION.md`.
2. Найди существующий активный Task Contract или Handoff.
3. Если их нет, выполни intake по `INTAKE.md`: определи тип работы, отдели
   независимо принимаемые результаты и сам создай Task Contract со статусом `DRAFT`.
4. Покажи пользователю компактный SCAM Preview. До подтверждения не меняй
   продуктовый код, конфигурацию и внешнее состояние.
5. После подтверждения поставь контракту статус `FROZEN` и начинай работу.
6. Если пользователь уже явно объявил acceptance замороженным и разрешил начать
   без повторного подтверждения, покажи превью как уведомление и продолжай.

Прямой ответ, объяснение или read-only lookup без проектного артефакта и
изменения состояния не требуют Task Contract. Не создавай методологическую
документацию ради самой документации.

## Перед началом замороженной задачи

1. Прочитай только перечисленные в Task Contract источники и непосредственно
   затронутый код, тесты и публичные контракты.
2. Проверь состояние Git и, для нескольких репозиториев, Workspace Baseline.
3. До изменений перечисли допущения. Не превращай допущения в требования.
4. Убедись, что тип задачи, owning gate и внешние полномочия определены.
5. Если Task Contract всё ещё содержит несколько независимо принимаемых
   результатов, верни `SPLIT` до реализации.

## Обязательные правила

- acceptance после начала реализации заморожен;
- новая находка не расширяет текущую задачу автоматически;
- отчёт агента не является доказательством;
- сохраняй чужие и незакоммиченные изменения;
- сначала узкая проверка, затем owning gate;
- reviewer классифицирует находки только как `BLOCKER`, `FOLLOW_UP` или
  `REJECTED`;
- `BLOCKER` обязан ссылаться на нарушенный пункт acceptance и воспроизводимое
  доказательство;
- не меняй методологию в рамках продуктовой задачи;
- не используй субагентов без независимой ограниченной подзадачи;
- не публикуй, не деплой и не выполняй внешние записи без соответствующего
  разрешения задачи;
- подробно документируй инженерно значимую работу: baseline, изменённое
  поведение, контракты, решения, проверки, ограничения и следующий шаг;
- перед `DONE` обнови живой Project Context и создай Work Record; отчёт в чате
  не заменяет проектную документацию;
- не записывай скрытые рассуждения, сырой transcript, секреты и шум временных
  попыток — фиксируй проверяемые факты и причины решений.

Завершение задачи допустимо только в одном состоянии:

- `DONE` — acceptance выполнен и подтверждён;
- `BLOCKED` — продолжение требует решения, доступа или внешнего изменения;
- `SPLIT` — задача слишком широка, реализация не начиналась или остановлена на
  безопасной границе.
