# Super Compact Agent Method

Минимальная методология разработки и ревью программных проектов с одним или
несколькими сервисами, пакетами или репозиториями.

Решает четыре задачи:

1. удерживает работу в заранее согласованном скоупе
2. не позволяет ревью бесконечно расширять DoD
3. требует исполняемые доказательства вместо отчётов агента
4. позволяет безопасно использовать субагентов только там, где они полезны

Методология не управляет моделями, стоимостью токенов и внутренними рассуждениями
агентов. Она регулирует только наблюдаемые действия и результаты.

## Установка

Скопируйте папку в корень проекта, например:

```text
your-project/
├── scam/
│   ├── AGENTS.md
│   ├── METHOD.md
│   └── templates/
└── ...
```

В корневом `AGENTS.md` проекта добавьте:

```markdown
Перед нетривиальной работой прочитай `scam/AGENTS.md` и следуй ему.
Проектные инструкции и архитектурные решения имеют приоритет над общей
методологией.
```

Если среда не читает `AGENTS.md` автоматически, начинайте новый чат фразой:

```text
Прочитай scam/AGENTS.md и работай по этой методологии.
Текущая задача: <задача>.
```

## Начало работы

1. Заполните `templates/WORKSPACE_BASELINE.json`, если проект состоит из
   нескольких репозиториев или версионируемых компонентов.
2. Для каждой задачи создавайте копию `templates/TASK.md`.
3. Передавайте reviewer копию `templates/REVIEW.md` вместе с task и diff.
4. Создайте живой `PROJECT_CONTEXT.md` по одноимённому шаблону.
5. После каждой завершённой задачи сохраняйте `WORK_RECORD.md`.
6. При смене чата обновляйте `templates/HANDOFF.md`.

Рекомендуемая структура проектной документации:

```text
docs/agent-context/
├── PROJECT_CONTEXT.md       # актуальное состояние, регулярно перезаписывается
├── work-records/            # фактические записи завершённых задач
│   └── <task-id>.md
└── handoffs/                # только незавершённые передачи между чатами
```

Подробные правила находятся в `DOCUMENTATION.md`. Документируется не поток
мыслей агента, а инженерно значимый контекст: что изменено, почему, какие
контракты затронуты, чем проверено и что осталось неизвестным.

## Что намеренно отсутствует

- автоматическая маршрутизация моделей
- обязательное делегирование
- система запретов и блокировок
- хуки, проверяющие формат ответов агента
- методологические эксперименты внутри бэклога
- автоматическое переоткрытие принятых задач
- требование читать всю документацию проекта
