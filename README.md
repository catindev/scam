# Super Compact Agent Method

Минимальная методология разработки и ревью программных проектов с одним или
несколькими сервисами, пакетами или репозиториями.

Решает пять задач:

1. превращает обычный пользовательский запрос в ограниченную единицу работы;
2. удерживает работу в заранее согласованном scope;
3. не позволяет review бесконечно расширять DoD;
4. требует исполняемые доказательства вместо отчётов агента;
5. позволяет безопасно использовать субагентов только там, где они полезны.

Методология не управляет моделями, стоимостью токенов и внутренними рассуждениями
агентов. Она регулирует только наблюдаемые действия и результаты.

## Установка

Скопируйте папку в корень проекта, например:

```text
your-project/
├── AGENTS.md
├── scam/
│   ├── AGENTS.md
│   ├── INTAKE.md
│   ├── METHOD.md
│   ├── DOCUMENTATION.md
│   └── templates/
└── ...
```

В корневом `AGENTS.md` проекта добавьте:

```markdown
Перед нетривиальной работой прочитай `scam/AGENTS.md` и следуй ему.
Проектные инструкции и архитектурные решения имеют приоритет над общей
методологией.
```

Если среда не читает `AGENTS.md` автоматически, достаточно начать новый чат:

```text
<Опишите задачу обычным языком>.

Прочитай scam/AGENTS.md и работай по SCAM.
```

Пользователь не должен самостоятельно переводить запрос в Task Contract.

## Как начинается работа

1. Агент читает entrypoint и выполняет ограниченный intake по `INTAKE.md`.
2. Он определяет тип задачи, при необходимости делит широкий запрос и сам
   создаёт Draft Task Contract.
3. Агент показывает короткий `SCAM Preview`: outcome, scope, acceptance,
   owning gate, внешние действия и существенные допущения.
4. Пользователь подтверждает понимание или поправляет конкретный пункт.
5. После подтверждения acceptance замораживается, и агент начинает работу по
   `METHOD.md`.

Пример превью:

```text
SCAM Preview
Type: IMPLEMENTATION
Task: ORDER-017 — idempotent checkout
Outcome: повтор одного checkout request не создаёт второй платёж
In scope: checkout handler, idempotency storage, integration test
Out of scope: новый payment API, deploy, migration старых заказов
Acceptance / owning gate: duplicate test + checkout integration gate
External actions: local branch/commit allowed; push/deploy forbidden
Assumptions or decisions: idempotency key уже является public contract
Split: deploy будет отдельной OPERATION task
```

Если пользователь уже дал замороженный acceptance и явно разрешил начинать без
ещё одного подтверждения, агент показывает превью как уведомление и продолжает.

Простые ответы, объяснения и read-only lookup не оборачиваются в Task Contract:
SCAM не должен создавать бюрократию там, где нет проектной работы.

## Проектные документы

Агент, а не пользователь:

1. заполняет `templates/WORKSPACE_BASELINE.json`, когда работа охватывает
   несколько репозиториев или версируемых компонентов;
2. создаёт Task Contract по `templates/TASK.md`;
3. использует `templates/REVIEW.md` для независимого review;
4. создаёт или обновляет живой Project Context;
5. сохраняет Work Record после завершённой задачи;
6. обновляет Handoff при смене чата до `DONE`.

Рекомендуемая структура проектной документации:

```text
docs/agent-context/
├── PROJECT_CONTEXT.md       # актуальное состояние, регулярно перезаписывается
├── tasks/                   # DRAFT/FROZEN Task Contracts
├── work-records/            # фактические записи завершённых задач
│   └── <task-id>.md
└── handoffs/                # только незавершённые передачи между чатами
```

Подробные правила находятся в `INTAKE.md`, `METHOD.md` и
`DOCUMENTATION.md`. Документируется не поток мыслей агента, а инженерно
значимый контекст: что изменено, почему, какие контракты затронуты, чем
проверено и что осталось неизвестным.

## Что намеренно отсутствует

- автоматическая маршрутизация моделей;
- обязательное делегирование;
- система запретов и блокировок;
- хуки, проверяющие формат ответов агента;
- методологические эксперименты внутри backlog;
- автоматическое переоткрытие принятых задач;
- требование читать всю документацию проекта;
- требование к пользователю вручную заполнять SCAM-шаблоны.

Всё это я, как автор этого пакета, уже пробовал и не нашёл пользы, кроме расхода
недельных лимитов агентов. Добавляйте автоматизацию только после повторяющейся
измеренной проблемы. Не расширяйте методологию на всякий случай и про запас.
