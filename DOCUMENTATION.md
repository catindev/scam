# Context documentation

## 1. Цель

Документация должна позволить новому человеку или чату восстановить рабочий
контекст без чтения переписки и без доверия к отчётам предыдущего агента.

Она обязана отвечать на вопросы:

- что представляет собой проект;
- из каких компонентов он состоит и кто чем владеет;
- какие решения и публичные контракты действуют сейчас;
- какая версия компонентов совместима между собой;
- что изменилось и почему;
- какие команды действительно выполнялись;
- что осталось незавершённым или неизвестным;
- какой следующий безопасный шаг.

Документация не является журналом внутренних рассуждений. Не сохраняй chain of
thought, сырой transcript чата, догадки без маркировки, многократные неудачные
варианты команд и несекретизированные логи.

## 2. Три обязательных документа

### Project Context — живой документ

Один актуальный файл проекта. Он регулярно обновляется и не хранит подробную
хронологию. Содержит:

- назначение и текущую цель;
- карту сервисов/модулей/репозиториев;
- ownership публичных контрактов;
- действующие архитектурные решения со ссылками;
- текущий совместимый baseline;
- стандартные команды запуска и gates;
- известные ограничения и активные риски;
- текущую задачу и следующий milestone;
- ссылки на последние Work Records.

Project Context — навигационный слой, а не замена коду, тестам и ADR. Любое
утверждение, которое можно проверить в canonical source, должно ссылаться на
него.

### Work Record — подробная запись задачи

Создаётся или обновляется перед `DONE`. Содержит:

- Task Contract и исходный baseline;
- исходную проблему и наблюдаемое поведение;
- изменённые файлы/компоненты;
- новое фактическое поведение;
- затронутые контракты, данные, migrations и compatibility;
- принятые решения и инженерное основание;
- важные отвергнутые варианты, если их повторение опасно;
- команды, окружение и результаты проверок;
- deployment/release действия, если они были разрешены;
- blockers, follow-ups и неопределённость;
- commit/PR/artifact/image digests.

Work Record не утверждает `PASS`, если команда не выполнялась. Используй
`NOT_RUN`, `BLOCKED` или `UNKNOWN`.

### Handoff — незавершённая передача

Создаётся только при смене исполнителя/чата до `DONE`. Он содержит состояние
рабочего дерева, выполненную часть, результаты проверок, незавершённые изменения
и один следующий шаг. После закрытия задачи canonical итогом становится Work
Record; старый Handoff можно архивировать.

## 3. Когда обновлять документацию

| Событие | Обязательное обновление |
| --- | --- |
| Изменён код без публичного контракта | Work Record; Project Context только если изменилось текущее состояние |
| Изменён API/message/schema/config contract | Work Record + canonical contract doc + Project Context |
| Принято архитектурное решение | ADR/decision record + Work Record + ссылка из Project Context |
| Добавлена migration | Work Record с forward/compatibility/rollback boundary |
| Изменён deployment/runbook | Canonical runbook + Work Record + команды в Project Context |
| Выполнен release/deploy | Work Record с точными commits/digests/environment |
| Найден повторяемый infra blocker | Короткий runbook после подтверждения причины |
| Задача прервана или передана | Handoff |
| Только локальное исследование без изменения решения | Результат в Work Record или task notes; Project Context не засорять |

## 4. Стандарт качества записи

Хорошая запись конкретна:

```text
POST /orders теперь возвращает 409 ORDER_IDEMPOTENCY_CONFLICT при повторном
ключе с другим payload. Проверено integration test X на commits A/B.
```

Плохая запись не проверяема:

```text
Улучшена идемпотентность, все тесты проходят.
```

Для каждого значимого утверждения указывай хотя бы один якорь:

- путь к коду или тесту;
- ADR/contract section;
- команда и результат;
- commit/PR;
- package/image digest;
- environment/run id.

## 5. Поддержание актуальности

- Project Context обновляется в той же задаче, которая сделала его устаревшим.
- Work Record после принятия задачи не переписывается для изменения истории;
  исправления добавляются как явно датированная коррекция или новая запись.
- Исторический документ не становится текущей инструкцией только потому, что он
  подробный.
- Дублирующий текст заменяй ссылкой на canonical source.
- Устаревшее утверждение удаляй из живого контекста, но сохраняй решение/историю
  там, где она нужна для объяснения миграции.
- Секреты, production payload и персональные данные не документируются.

## 6. Проверка перед завершением

Перед `DONE` ответь:

1. Сможет ли новый чат назвать точные затронутые компоненты и commits?
2. Поймёт ли он новое поведение и причины решения?
3. Сможет ли он повторить проверки без истории чата?
4. Видит ли он, что не проверялось?
5. Однозначен ли следующий milestone?

Если нет — документация задачи неполна.
